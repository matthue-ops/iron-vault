# Refund usability and member entry feedback — 11-item batch

Implementation only; no SQL, deployment, real check-in, top-up, refund or email is executed by the agent. The user approved preparing this database change under AGENTS.md rule 13. The earlier operational-safeguards batch is separate; this document describes only the newly authorized 11 items.

## Implemented scope

1. **Uniform menu:** every visible owner/staff item uses 14px/600 text, a fixed icon column, 44px minimum row height, matching hover/focus states. Membership Pricing → Refunds → My Account; Sign Out has a divider. Existing permission filtering stays in force.
2. **Readable Activity:** refund actions use clear titles, member name/code, amount, reason, immutable request reference, and approved source/recipient balance changes. Pending requests explicitly say no balance changed. Raw internal identifiers are collapsed under Technical details in the table, retained in exports. Legacy refund events are enriched at read time where the linked case remains available, without rewriting original logs or inventing a new historical actor.
3. **Refund member search/recent transactions:** search by name or member code/internal ID. Recent Transactions contains the latest 10 gym sources with member and transaction details. An explicit selection fills the form.
4. **Newest original transactions first:** sort by transaction timestamp descending with a deterministic key tiebreaker; readable date, type, remaining eligible amount and short reference if one exists. Full original IDs remain in the review's Technical details.
5. **Conditional reason:** only Other reveals a required Specify reason. Standard presets supply the actual recorded reason; the final text appears in review.
6. **Generated request reference:** remove the editable request Reference / receipt input. The first Review request reserves the code on the server; it remains read-only, tied to the stable request UUID and requester through editing/retries, approval, notices and history. Actual cash payout receipt is a separate saved field and never overwrites it.
7. **Conditional recipient:** visible only for Correct incorrect wallet credit; searchable by name/member code. Changing action clears it. Other correction reasons may omit a transfer; wrong-account correction requires an active same-gym recipient different from the source member.
8. **Full wrong-account correction:** selecting the source/action/reason fills the full remaining amount read-only. Previously adjusted or spent credit produces a warning and cannot silently produce a smaller transfer. Server request and approval checks enforce recipient/full amount again. Existing pre-044 requests retain their prior review semantics.
9. **Separate review windows:** New → Review → Edit retains all form selections/reason/code. Only a successful Confirm request resets the draft and opens Pending review. Approval has its own window; Back returns to the unchanged pending card, where a rejection reason can be entered. Errors retain the form/window for correction or retry. Sign-out/account changes clear private UI. Draft identity survives a page reload; form values are kept in memory during the session, not written as personal information to browser storage. A full page reload still requires re-entering unsaved form values. A committed case found on reload clears its completed draft identity.
10. **Six-character top-up/refund references:** uppercase `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`; excludes O/0/I/1. A private registry enforces uniqueness within the gym across both types, using cryptographically random UUID bytes, collision retries and a stable identity key. Full UUIDs remain authoritative. New top-up success, own financial notice and reports display the short code. Replaying the same financial request returns the same code. Existing records are not automatically backfilled or renamed. A legitimate retry of an old saved top-up may allocate its first short code without another financial transaction; prior notices remain unchanged.
11. **Method-specific member feedback:** the profile banner and online success window read the confirmed latest attendance method. QR retains QR ACCEPTED; manual shows Entry Granted / Checked in by gym staff / Philippine time. A neutral Entry Granted label is used when a legacy record has no method. Initial load, offline/reconnect, returning to the tab and browser restoration establish a baseline; no old success popup is replayed. An online fresh event opens once per entry, closes in 2.5 seconds, and remains in existing attendance history. Server time is included with the latest entry to assess freshness without relying on the device clock when available.
